# Technical & IP Diligence Review — Document Structure Template

The standard structure for every Technical & IP Diligence Review generated by the Python app: a single-page
investor document assessing a company's technical architecture, development maturity and intellectual-property
position for later-stage financing, strategic investment, acquisition or exit diligence.

This template defines **structure, fields and format only**. It contains no company data. Placeholders use
`{{field.path}}`, where the path is the field in the app's `DiligenceAnalysis` JSON
(`app/models/schemas.py`). A machine-readable copy of this template is in
[`tech_ip_review_template.json`](tech_ip_review_template.json).

---

## 1. Page Specification

| Property | Value |
|---|---|
| Page size | US Letter, portrait (8.5" × 11") |
| Page count | **Exactly one page.** A second page is never allowed |
| Margins | Left/right 0.42", top 0.34", bottom 0.52" (footer zone) |
| Body font | Open Sans (fallback: Helvetica), 6.3–7.3 pt depending on density level |
| Section headings | Bold, 7.6 pt, navy, uppercase, orange rule beneath |
| Header | None. The navy title band is part of the page body |
| Footer | TEN Capital house footer (see §10) |

## 4. Section 1 — Company Snapshot

### 4.1 Snapshot grid (2 rows × 4 columns)

Each cell shows a small uppercase grey label above a bold value.

| Row | Column 1 | Column 2 | Column 3 | Column 4 |
|---|---|---|---|---|
| 1 | **Sector** `{{company.sector}}` | **Stage** `{{company.stage}}` | **Revenue** `{{company.revenue}}` | **Growth** `{{company.growth}}` |
| 2 | **Gross Margin** `{{company.gross_margin}}` | **Customers** `{{company.customers}} · {{company.customer_concentration}}` | **Funding / Raise** `{{company.raise_amount}} · {{company.funding_to_date}}` | **Development Maturity** `{{development_maturity.level}}` |

Cell rules:
- Values are truncated at 48 characters (60 for Customers and Funding / Raise).
- A field classified INFERENCE or ASSUMPTION is followed by a small grey `(inferred)`.
- A missing field shows grey italic `Not provided`.
- Development Maturity shows `Not provided` when the level is `Not determinable`.

Snapshot fields that are extracted but not printed in the grid still go to the JSON output and the TEN Capital
record: `company.name`, `company.product` and `company.engineering_team`.

### 4.2 Category score strip (1 row × 10 cells)

One cell per scoring category, in this order:

| # | Short label | Category (`scores.categories[].category`) | Weight |
|---|---|---|---|
| 1 | Architecture | `technical_architecture` | 15% |
| 2 | Maturity | `development_maturity` | 10% |
| 3 | Scalability | `scalability` | 10% |
| 4 | Eng. Org | `engineering_organization` | 10% |
| 5 | Docs | `technical_documentation` | 5% |
| 6 | Security | `cybersecurity_compliance` | 10% |
| 7 | IP Owner. | `ip_ownership` | 15% |
| 8 | IP Defens. | `ip_defensibility` | 10% |
| 9 | 3rd Party | `third_party_dependency` | 5% |
| 10 | Exit Ready | `exit_readiness` | 10% |

Cell format: `{{short label}}` / **`{{score}}`**`/5 · {{weight}}%`.
- The score number is colored by value (§12).
- When `evidence_status` is `NOT PROVIDED`, the number is grey with a tiny `unverified` note beneath.

## 5. Section 2 — Technical Assessment (left column)

Each row is a paragraph: **`{{Label}}:`** (navy bold) followed by the finding text. Inline slide references use the
form `(S#, S#)`. The literal `NOT PROVIDED` is highlighted in bold orange.

| Order | Label | Source field | Content expected |
|---|---|---|---|
| 1 | Architecture | `technical_architecture.summary` | Concerns, supporting evidence, and gaps across: architecture style, hosting/deployment, redundancy/failover, observability, APIs/integrations, single points of failure, legacy or customer-specific components |
| 2 | Development maturity | `development_maturity.level` — `development_maturity.rationale` | Maturity classification (§12), followed by the evidence behind it. Roadmap items are never counted as completed |
| 3 | Scalability | `scalability.summary` | Scaling approach, load/capacity evidence, cost to serve, and economic risks (inference, services, hardware, margin) |
| 4 | Engineering org | `engineering_organization.summary` | Technical leadership, team size, in-house vs. contractor development, key-person dependency |
| 5* | Security / compliance | `cybersecurity.summary` | Attestations, penetration testing, encryption/access control, DR, incident response, and the frameworks relevant to the sector |
| 6* | AI / data | `ai_data.proprietary_assessment` | Shown only when `ai_data.applicable` is true. States whether the AI advantage is proprietary or built on third-party models |

Summary text pattern (rules engine), in this order: `Concerns: … Evidence: … Planned only: … Not provided: …`

## 6. Section 3 — Intellectual Property (right column)

Same row format as Section 2.

| Order | Label | Source field | Content expected |
|---|---|---|---|
| 1 | Core IP | `intellectual_property.core_ip` | Proprietary assets identified: patents, datasets, algorithms, trade secrets |
| 2 | Ownership | `intellectual_property.ownership` | Invention assignments, company ownership, founder/university/government/prior-employer/joint-development rights, contractor-created code |
| 3 | Defensibility | `intellectual_property.defensibility` | Moat evidence and weakening factors. Always states that patents are not proof of defensibility, and that there is no freedom-to-operate evidence unless the deck provides it |
| 4 | Patents | `intellectual_property.patents` | Issued, pending or planned filings. Claim coverage, ownership records and expiry are marked not evidenced unless stated |
| 5 | Trade secrets | `intellectual_property.trade_secrets` | Trade secrets or proprietary know-how, and whether protection controls are evidenced |
| 6 | Software / data | `intellectual_property.software_data` | Contractor-created code, open-source and copyleft usage, license compliance, licensed components, data rights |
| 7 | Third-party | `intellectual_property.third_party` | Top dependencies as `Name (type, criticality)`; source is `third_party_dependencies[]` |

## 7. Section 4 — Top Risks

A three-column table with a navy rule under the header and alternating light-grey row shading.

| Column | Width | Header | Cell content |
|---|---|---|---|
| 1 | 52 pt | SEVERITY | `{{red_flags[i].severity}}` as a white bold chip on the severity color (§12) |
| 2 | 262 pt | ISSUE & EVIDENCE | **`{{red_flags[i].issue}}`**, then on a new line in small grey: `{{red_flags[i].classification}} · {{red_flags[i].evidence}}` |
| 3 | remainder | BUSINESS CONSEQUENCE & MITIGATION | `{{red_flags[i].business_consequence}}` **Mitigate:** `{{red_flags[i].mitigation}}` |

Row rules:
- 3–5 rows, taken from `red_flags[]`, which is sorted most severe first (CRITICAL → HIGH → MEDIUM → LOW; FACT before INFERENCE before NOT PROVIDED).
- If fewer than three material flags exist, the list is topped up with LOW `EVIDENCE_GAP` items drawn from `missing_information[]`.
- If there are no flags at all, print one row: `— │ No material red flags identified from deck evidence. │ Verify deck claims against the data room.`

Each `red_flags[]` entry in the JSON must carry every field below, even though the PDF prints only a subset:

| Field | Description |
|---|---|
| `code` | Flag type identifier |
| `category` | Scoring category affected |
| `issue` | One-line statement of the issue |
| `severity` | CRITICAL / HIGH / MEDIUM / LOW |
| `classification` | FACT / INFERENCE / NOT PROVIDED |
| `evidence` | `S#: "verbatim excerpt"`, or `Not addressed anywhere in the deck.` |
| `slides` | Supporting slide numbers (empty for NOT PROVIDED) |
| `business_consequence` | Why it matters to a financing or transaction |
| `diligence_question` | The question that resolves it |
| `mitigation` | Suggested remediation |
| `exposures` | How it surfaces in a transaction (§12) |

## 8. Section 5 — Exit / Deal-Closing Exposure (left column)

| Element | Source field | Format |
|---|---|---|
| Summary | `exit_readiness.summary` | Body paragraph: which issues could become significant in later-stage financing, strategic investment, licensing or acquisition diligence |
| Exposure bullets | `exit_readiness.exposures[]` (CRITICAL, HIGH, MEDIUM only) | `• ` in the severity color, then **`{{issue}}`** `› {{exposure_types}}` in grey, listing up to 3 exposure types. "Diligence question" is omitted when stronger exposure types are present |

Summary patterns:
- **Critical issues exist:** `{{n}} issue(s) likely to become closing conditions, escrow or indemnity items: {{issues}}.`
- **High issues only:** `No closing blockers identified from the deck; high-severity items likely to drive diligence questions and reps & warranties: {{issues}}.`
- **Neither:** `No critical or high-severity transaction exposures identified from deck evidence.`

---

## 9. Section 6 — Priority Diligence Questions (right column)

Exactly five numbered questions, taken from `diligence_questions[0..4]`:

`{{priority}}.` (orange bold) `{{question}}` `[{{audience}}]` (small grey)

**Audience values:** Investor, Technical advisor, IP counsel, CTO, CISO, Acquirer. Combinations such as `CTO / IP counsel` are allowed.

**Priority order:**
1. Questions for CRITICAL flags
2. Questions for HIGH flags
3. Model-raised questions
4. Questions for MEDIUM flags
5. Baseline questions for categories scoring 3 or lower
6. Questions for LOW flags
7. Remaining baseline questions

Near-duplicate questions are removed, so all five are distinct lines of inquiry.

## 10. Section 7 — Investor Conclusion

A full-width box on a light tint (`#EEF3F9`) with a 4 pt orange bar on its left edge.

| Element | Source field | Allowed values | Format |
|---|---|---|---|
| Heading | — | `INVESTOR CONCLUSION` | Section-heading style |
| Chip 1 | `investor_conclusion.technical_position` | Strong / Adequate / Mixed / Weak / High Risk | Grey label `TECHNICAL POSITION`; value bold, colored by rating |
| Chip 2 | `investor_conclusion.ip_position` | Strong / Adequate / Mixed / Weak / High Risk | Grey label `IP POSITION` |
| Chip 3 | `investor_conclusion.transaction_readiness` | Ready / Mostly Ready / Material Diligence Required / Significant Remediation Required | Grey label `TRANSACTION READINESS` |
| Conclusion | `investor_conclusion.summary` | 2–3 sentences, max 520 chars | Body text |

Conclusion sentence pattern:
1. `On deck evidence, {{company}} rates {{technical_position}} on technology and {{ip_position}} on IP (score {{overall_score}} ± {{uncertainty}}; evidence confidence {{evidence_confidence}}/100).`
2. The most material issue and how it would surface in a transaction. With no critical or high flags, state that no such issues surfaced and that verification is still required.
3. `Transaction readiness: {{transaction_readiness}}.` When confidence is below 50, add a caveat that limited disclosure means scores could move materially.

## 12. Fitting Rules (One-Page Guarantee)

The page is rendered at the least-compressed density level whose content fits. Each level shortens
lower-priority text first.

| Limit | Level 0 (default) | Level 5 (tightest) |
|---|---|---|
| Body font size | 7.3 pt | 6.3 pt |
| Technical row text | 240 chars | 95 chars |
| IP row text | 190 chars | 80 chars |
| Top-risk rows | 5 | 3 |
| Risk issue | 110 chars | 80 chars |
| Risk evidence line | 130 chars | omitted |
| Consequence | 150 chars | 80 chars |
| Mitigation | 110 chars | omitted |
| Diligence question | 180 chars | 110 chars |
| Exposure bullets | 4 | 2 |
| Exit summary | 220 chars | 90 chars |
| Conclusion | 520 chars | 320 chars |
| Security / compliance row | shown | omitted from level 3 |
| AI / data row | shown | omitted from level 2 |

Compression priority:
1. Compress repetitive wording.
2. Shorten lower-priority observations.
3. Preserve the highest-risk issues (never fewer than 3 rows).
4. Preserve all 5 diligence questions.
5. Preserve the investor conclusion.

If content still overflows, a final shrink-to-fit pass is applied. The rendered file is then checked, and a
second page raises an error instead of being written. Text is truncated at a word boundary and marked with `…`.
It is never clipped mid-word or overlapped.

## 13. Field Values, Enumerations & Visual Codes

### 13.1 Evidence classification (every finding, snapshot field and red flag)

| Value | Meaning |
|---|---|
| FACT | Directly supported by the uploaded materials. Must carry slide number(s) and a verbatim excerpt |
| INFERENCE | Reasonable interpretation of available evidence |
| ASSUMPTION | Used because required information was unavailable |
| NOT PROVIDED | Information necessary for diligence that cannot be found |

### 13.2 Category scores (1–5) and colors

| Score | Rubric | Color |
|---|---|---|
| 5 — Strong | Well-supported evidence, mature practices, limited material risk | `#1F7A4D` |
| 4 — Good | Generally strong with manageable gaps | `#3F8A3A` |
| 3 — Moderate | Material unanswered questions requiring diligence | `#A86B12` |
| 2 — Weak | Meaningful technical or IP concerns | `#D9531E` |
| 1 — High Risk | Potential financing, transaction, scalability or ownership issue | `#B42318` |
| Unverified | No deck evidence for the category | `#8A94A3` |

**Overall Technical & IP Diligence Score** = weighted category average mapped to 0–100 (1 → 0, 5 → 100), printed as
`{{score}} ±{{uncertainty}}`.

**Evidence Confidence** = 0–100, capped at 85 for deck-only evidence.

### 13.3 Red-flag severity and colors

| Severity | Meaning | Chip color |
|---|---|---|
| CRITICAL | Could materially prevent investment, acquisition, financing, licensing or closing | `#B42318` |
| HIGH | Likely to become a major diligence issue or require remediation | `#E85D26` |
| MEDIUM | Should be investigated but appears manageable | `#A86B12` |
| LOW | Minor gap or documentation issue | `#5B7083` |

### 13.4 Development maturity levels

Experimental · Prototype · Early Production · Production · Scaled Production · Enterprise-Grade · Not determinable

### 13.5 Position ratings and colors

| Adequate | `#3F8A3A` |
| Mixed | `#A86B12` |

### 13.6 Transaction readiness and colors

### 13.7 Transaction exposure types

Diligence question · Closing condition · Reps & warranties · Indemnity · Escrow / holdback · Purchase-price

## 14. Companion Outputs (not printed, same structure)

Every generated review is accompanied by:

1. **Structured analysis JSON.** The complete `DiligenceAnalysis` object: `company`, `source_evidence`,
   `technical_architecture`, `development_maturity`, `engineering_organization`, `technical_documentation`,
   `cybersecurity`, `intellectual_property`, `ai_data`, `third_party_dependencies`, `scalability`,
   `exit_readiness`, `scores`, `evidence_confidence`, `red_flags`, `diligence_questions`, `assumptions`,
   `missing_information`, `investor_conclusion`, `warnings`.
2. **TEN Capital record JSON.** Contents:
   - user, company, sector, stage, raise amount, revenue, growth, gross margin;
   - overall score, uncertainty, evidence confidence;
   - the ten category ratings and the maturity level;
   - technical position, IP position, transaction readiness;
   - critical and high-severity red flags;
   - top five diligence questions;
   - major missing information, summary findings, recommended diligence areas;
   - consent status (default `NOT_GRANTED`), transmission status, report timestamp, source file and hash, engine.
